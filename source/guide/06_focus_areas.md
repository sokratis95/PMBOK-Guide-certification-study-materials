# Chapter 6 — Focus Areas and the 40 Processes

**After this chapter you should be able to:**
- describe the purpose of the five focus areas and how they repeat during a project;
- place each of the 40 processes in its performance domain and focus area;
- translate Sixth-Edition process names into Eighth-Edition names;
- explain inputs, tools and techniques, and outputs (ITTOs) and the most common ones;
- list the components of the project management plan, the main project documents and the baselines;
- distinguish work performance data, information and reports.

## 6.1 The five focus areas

The Eighth Edition calls the former *process groups* **focus areas**. A focus area is a logical grouping of processes by the *nature of the work* — not a phase of the project. All five can occur within each phase, release or iteration, and they overlap.

| Focus area | Purpose | Typical key outputs |
|---|---|---|
| **Initiating** | Define a new project or phase, obtain authorisation, align stakeholders on purpose | Project charter, assumption log, stakeholder register |
| **Planning** | Establish the scope, refine objectives and define how the work will be done | Project management plan, baselines, subsidiary plans, project documents |
| **Executing** | Perform the work defined in the plan, lead people, manage engagement and communications | Deliverables, work performance data, issue log, change requests |
| **Monitoring and Controlling** | Track, review and regulate progress and performance; identify needed changes; validate and control deliverables | Work performance information and reports, approved/rejected changes, accepted deliverables, forecasts |
| **Closing** | Formally complete the project, phase or contract | Final product transition, final report, archives, lessons learned |

> **Exam tip.** **Monitoring and Controlling runs in parallel with all other focus areas** — from the first day to the last. And in adaptive approaches all five focus areas occur inside every iteration: planning (sprint planning), executing (development), monitoring and controlling (daily scrum, sprint review), closing (iteration closure) — and initiating when a new release or phase starts.

How many processes per focus area? **Initiating 2 · Planning 19 · Executing 8 · Monitoring and Controlling 10 · Closing 1 = 40.**

| Domain | Initiating | Planning | Executing | Monitoring & Controlling | Closing |
|---|---|---|---|---|---|
| **Governance (9)** | Initiate Project or Phase | Integrate and Align Project Plans · Plan Sourcing Strategy | Manage Project Execution · Manage Quality Assurance · Manage Project Knowledge | Monitor and Control Project Performance · Assess and Implement Changes | Close Project or Phase |
| **Scope (6)** | | Plan Scope Management · Elicit and Analyze Requirements · Define Scope · Develop Scope Structure | | Validate Scope · Monitor and Control Scope | |
| **Schedule (3)** | | Plan Schedule Management · Develop Schedule | | Monitor and Control Schedule | |
| **Finance (4)** | | Plan Financial Management · Estimate Costs · Develop Budget | | Monitor and Control Finances | |
| **Stakeholders (7)** | Identify Stakeholders | Plan Stakeholder Engagement · Plan Communications Management | Manage Stakeholder Engagement · Manage Communications | Monitor Stakeholder Engagement · Monitor Communications | |
| **Resources (5)** | | Plan Resource Management · Estimate Resources | Acquire Resources · Lead the Team | Monitor and Control Resourcing | |
| **Risk (6)** | | Plan Risk Management · Identify Risks · Perform Risk Analysis · Plan Risk Responses | Implement Risk Responses | Monitor Risks | |

Patterns that help you memorise the table:

- Every domain except Governance and Stakeholders has a **"Plan … Management"** process that creates its management plan (Plan Scope Management, Plan Schedule Management, Plan Financial Management, Plan Resource Management, Plan Risk Management); Stakeholders has *Plan Stakeholder Engagement* and *Plan Communications Management*, and Governance has *Integrate and Align Project Plans* (the integrated plan) and *Plan Sourcing Strategy*.
- Every domain has at least one **monitoring and controlling** process.
- Governance is the only domain with processes in **all five** focus areas.
- Only **Initiate Project or Phase** and **Identify Stakeholders** are initiating processes; only **Close Project or Phase** is a closing process.

Arithmetic check: 49 − 3 (schedule merges) − 1 (risk analysis merge) − 1 (team merge) − 1 (quality planning) − 1 (quality control) − 2 (conduct and control procurements absorbed) = **40**.

> **What changed.** The Eighth Edition states that its processes are **non-prescriptive**: they describe work that is commonly needed, but the team decides — through tailoring — which processes to use, how formally, and how often. Don't expect the exam to ask you to recite inputs and outputs; expect it to test whether you know what a process is *for* and what it *produces*.

## 6.4 Anatomy of a process: ITTOs

Each process is described by:

- **Inputs** — what you need to perform it (documents, plans, data, environmental factors);
- **Tools and techniques** — how you transform the inputs (methods, analyses, meetings);
- **Outputs** — what the process produces (artifacts, deliverables, decisions, updates).

Outputs of one process are often inputs to another — this is how processes **interact**.

### The most common inputs

| Input | Notes |
|---|---|
| **Project management plan** (or a component of it) | The integrated plan and its subsidiary plans and baselines |
| **Project documents** | Logs, registers, estimates, schedules — documents that are *not* part of the plan |
| **Enterprise environmental factors** | Culture, market, regulations, infrastructure |
| **Organisational process assets** | Policies, templates, historical information, lessons learned |
| **Business documents** | Business case, benefits management plan (mainly in initiating) |
| **Agreements** | Contracts with customers or suppliers |
| **Work performance data/information** | Status data from execution and control |

### The most common tools and techniques (by family)

| Family | Examples |
|---|---|
| **Expert judgment** | Advice from individuals or groups with specialised knowledge |
| **Data gathering** | Brainstorming, interviews, focus groups, questionnaires and surveys, benchmarking, checklists |
| **Data analysis** | Alternatives analysis, root-cause analysis, variance analysis, trend analysis, earned value analysis, what-if scenario analysis, reserve analysis, SWOT, assumption and constraint analysis |
| **Data representation** | Charts and diagrams, matrices, mind maps, affinity diagrams, stakeholder grids, histograms |
| **Decision-making** | Voting (unanimity, majority, plurality), autocratic decision, multicriteria decision analysis |
| **Communication skills** | Feedback, presentations, active listening |
| **Interpersonal and team skills** | Facilitation, conflict management, negotiation, influencing, leadership, emotional intelligence, meeting management |
| **Estimating** | Analogous, parametric, bottom-up, three-point |
| **Meetings** | Kickoff, planning, status, review, retrospective, change control board meetings |
| **Project management information system (PMIS)** | Scheduling software, dashboards, configuration management tools, AI-assisted analytics |

## 6.5 The project management plan and project documents

The **project management plan** describes how the project will be executed, monitored and controlled, and closed. It integrates:

**Subsidiary management plans** — scope management plan, requirements management plan, schedule management plan, financial (cost) management plan, quality management plan (quality planning is part of defining scope in the Eighth Edition, but a quality plan is still a component), resource management plan, communications management plan, risk management plan, sourcing (procurement) strategy plan, stakeholder engagement plan.

**Baselines** — scope baseline, schedule baseline, cost baseline (together the **performance measurement baseline, PMB**).

**Additional components** — change management plan, configuration management plan, performance measurement baseline, project life cycle description, development approach, management reviews.

**Project documents** (not part of the plan, updated freely as the project progresses — no formal change control needed): activity attributes and list, assumption log, basis of estimates, change log, cost estimates, duration estimates, issue log, lessons learned register, milestone list, physical resource assignments, project calendars, project communications, project schedule, network diagram, project scope statement*, project team assignments, quality control measurements, quality metrics, quality report, requirements documentation, requirements traceability matrix, resource breakdown structure, resource calendars, resource requirements, risk register, risk report, schedule data, schedule forecasts, stakeholder register, team charter, test and evaluation documents.

\* The project scope statement is also part of the scope baseline once approved.

> **Trap.** Updating the **issue log**, **risk register** or **lessons learned register** does **not** require a change request — they are project documents. Changing a **baseline** or the **project management plan** does.

### The baselines

| Baseline | Components | Changed only through |
|---|---|---|
| **Scope baseline** | Approved project scope statement + WBS (scope structure) + WBS dictionary | Formal change control |
| **Schedule baseline** | Approved version of the schedule model with baseline start and finish dates | Formal change control |
| **Cost baseline** | Approved time-phased budget, *excluding management reserves*, including contingency reserves | Formal change control |
| **Performance measurement baseline (PMB)** | Integrated scope-schedule-cost baseline used for earned value management | Formal change control |

## 6.6 Data → information → reports

| Term | Created in | Example |
|---|---|---|
| **Work performance data** | Executing (Manage Project Execution and other executing processes) | Raw observations: "Activity 4.2 is 60% complete; actual cost $12,000; 3 defects found" |
| **Work performance information** | Monitoring and controlling processes | Data compared with the plan and analysed: "CPI = 0.86; activity 4.2 is 5 days late; defect rate above threshold" |
| **Work performance reports** | Monitor and Control Project Performance | Compiled for decisions and communication: status reports, dashboards, heat maps, forecasts |

> **Exam tip.** A question that says "the team reports that 70% of the work is complete" is describing **data**. Once compared with the plan ("we are 10% behind"), it becomes **information**. Assembled into a dashboard for the steering committee, it becomes a **report**.

## 6.7 Change requests: the four types

Executing and monitoring processes produce **change requests**, which go through *Assess and Implement Changes*:

| Type | Purpose |
|---|---|
| **Corrective action** | Realign *current* performance with the plan (e.g., add a tester because testing is behind) |
| **Preventive action** | Ensure *future* performance stays aligned with the plan (e.g., train the team before a new technology is used) |
| **Defect repair** | Modify a non-conforming product or component |
| **Update** | Change formally controlled documents or plans to reflect modified or additional ideas or content |
